## Causal source map and contract limits

Paths below are mobile-relative unless prefixed Go.

- `SpofifyApplication.kt:30–60,101–164`: one AppGraph per Application/process; `configure` replaces client/coordinator; `restore` preserves an already-live session. `endCoordination()` closes the coordinator then immediately cancels its parent scope; configure/clear additionally cancel the old HTTP dispatcher and clear authentication.
- `MainActivity.kt:76–79,119–145`, `LibraryViewModel.kt:220–225,749–756`, `playback/PlaybackConnection.kt:183–295`: Activity ViewModel/controller ownership is separate from graph/service ownership. Picker and expanded sheet are presentation. A still-valid service must not register twice when its controller is released/rebound. Do not accidentally fix graph teardown by making Compose own a coordinator/player.
- `feature/devices/PlaybackCoordinator.kt:294–334,388–401`: service activation starts heartbeat; deactivation fences output, clears registration, cancels work children, then launches one `leave(oldId)` in the **parent scope**. Graph teardown immediately cancels that same scope. The leave's timeout is currently **inside** the transport mutex, so bounded HTTP alone is not a bounded cleanup lifetime. Prove what runs when the lock/request is held; do not equate launching cleanup with completing it.
- Coordinator `register():883–905`, `request():1014–1034`: every successful register is fresh. Unknown outcome backs off 8s, 16s, then at most 30s. A response accepted server-side but lost/discarded after lifecycle change leaves no known ID to leave. The next register can precede the old registration's 30s expiry. Backoff is not registration idempotency; service/graph replacement can reset memory-only ambiguity tracking.
- `playback/PlaybackService.kt:onCreate/onTaskRemoved/onDestroy/settleTerminalOutput` and `PlaybackConnection.release`: distinguish a controller-only detach, a still-started/foreground healthy player and actual disposal. A genuinely disposed service gets a new receiver incarnation; neither registration reuse nor a new receiver may inherit old audio authority.
- `feature/devices/PlaybackDeviceIdentity.kt` persists encrypted origin/account-bound installation UUID and accepted name. **Neither is the ephemeral device ID, receiver ID, session identity or lease.** Core `PlaybackDevicesApi.register` sends name plus negotiated capability, not installation UUID.
- Go `internal/web/playback.go:574–587`: register always allocates a random ID, bound to account AND session digest; same cookie does not identify one installation. `:591–606` permits leave/poll only for that session's exact registration (rename is account-wide presentation). Do not persist/reuse authority, delete by name, or assume all IDs in the same session belong to this installation.
- Go `internal/web/queue_intent.go:114–142` rejects a receiver incarnation already retained by another registration, and changing incarnation within an existing registration. A **same-service** coordinator/reregistration transition with an orphan old row can therefore fail publication independently of display identity; test this explicitly. A genuinely new service must have a fresh receiver ID. Do not rotate incarnations to evade the rule without proving lifetime/authority ownership.
- Go `:259–320,377–385,707–861`: request-driven session verification/pruning, availability **<=5s**, registration expiry **>=30s**, owner lease **8s**, startup quarantine **8s**, normal command/transfer ACK **8s**, room maximum **16**. Transient session lookup errors do not establish revocation. Explicit owner leave acknowledges local silence and clears quarantine; uncertain disappearance drains the last lease. Prepare is silent; release ACK is proof the source stopped; activate grants a new epoch and needs an actual state/result ACK. Directives are delivered once, not retried. A valid poll advances waiting transfer after drain; GET does not. Do not replace these rules with a stronger fake.

**Unsolvable completely in this mobile-only unit:** death after register acceptance before receiving/consuming ID; lost register response with unknown late server execution; death before/during leave; lost leave acknowledgement; relaunch while prior lease/row remains. Current broker has no installation-bound registration recovery/idempotency/replacement. Immediate single-row identity through every crash window cannot honestly be guaranteed. A mobile timeout is not an upper bound on when a delayed server write commits; a fixed local sleep is not proof an orphan has expired. State these residual windows explicitly. If zero transient duplicate registrations after abrupt death is mandatory, escalate the missing broker capability through parent with a minimal evidence-backed requirement; do not implement a new wire protocol or block the correct mobile graceful/reattach fix on speculative backend work.

## Required behavior

1. **Presentation and live reattachment:** picker open/dismiss/reopen, expanded collapse/expand, Activity recreation, background/foreground and service/controller rebinding to the same live service retain the one graph/registration/receiver/player. Assert zero register/leave/select/acquire/prepare/start/history side effects from presentation alone. An allowed read-only empty-view refresh is not registration.
2. **Graceful actual disposal:** synchronously silence/revoke the retiring output and release focus/foreground resources, then give its known exact registration one bounded lifecycle-owned cleanup opportunity before retiring the resources needed by that attempt. Cleanup must survive cancellation of ordinary work but cannot indefinitely retain a graph, credentials or dispatcher; include lock wait in the bound. Serialize old disposal/new registration where needed within the owning app lifetime. Old completions cannot clear, unregister, silence or publish into a successor service/client/session. No blind uncertain-write retries. Do not retain a service forever merely to advertise a paused/dead endpoint.
3. **Abrupt loss/uncertainty:** fail closed and truthful, suppress avoidable registration churn, and respect server expiry/drain rather than claiming instant cleanup. Known old IDs may be used only for an explicitly safe same-session disposal operation, not authority restoration; no new durable authority store. Unknown accepted registrations must not be guessed from display names or the list. Once a known stale row becomes unavailable/expired, the view must reflect the real broker state and selection must remain usable. Explain any unavoidable transient row, including its safety/recovery behavior, without cosmetic deduplication.
4. **Select exact endpoints:** new genuine endpoints with the **same display name** remain separate/selectable by device ID. A row selection has an exact issuer/target/session/lifecycle/selection-sequence identity, accepted versus terminal state and matching pending token. Test old A → B → A, selecting self during drain, latest choice replacing pending work, target disappearing and late old responses. An old registration is not this phone just because its name matches. No disabled whole picker/endless ring after a terminal rejection, orphan timeout or expired registration; require a fresh explicit action when policy requires it, not deferred hidden takeover.
5. **No passive authority repair:** reopening/reconnect/restoration never selects or autoplays and never imports server display as audible state. Preserve explicit app first-Play's exact-self/current-epoch **`requireUnselected:true`** guarded admission and its terminal ACK gate. Queue-only Low/High/Next never claim output. Unavailable selected remote is still selected: no local stealing/fallback. Existing successful active playback survives UI-only detach.
6. **Authentication distinctions:** same origin/account/**same persisted session cookie** across successive graph/process simulations is the primary regression. Separately expire/revoke session, log out, reauthenticate to equal account values, and change account/origin. Old registrations/callbacks cannot borrow the successor session. Never delay actual logout's security revocation waiting indefinitely for cleanup.
