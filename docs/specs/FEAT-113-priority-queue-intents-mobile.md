## Required behavior

Replace blanket remote contextual rejection with the same explicit **Low / High / Next / Now** intents on the selected capable output. One receiver-authoritative transaction prepares exact selection, rechecks authority, performs placement/selection, then starts only if that operation changes the exact current selection; never sample mobile playing state to choose Play versus Add.

| Intent | Placement and identity |
| --- | --- |
| Low | Append the selected ordered batch after the existing future; do not mark pending High. |
| High | FIFO after the **last pending High occurrence**, otherwise after current, ahead of the ordinary Low tail. Preserve existing explicit interleaving; do not repartition on insertion. |
| Next | Immediately after current; marks pending High but retains requested origin Next. Repeated deliberate Next may put the newest request first. |
| Now | Track/collection selection deliberately replaces with its exact prepared context and selected occurrence (collection selects first); new context tail Low. Existing upcoming selection instead jumps that exact key without replacement, copying or refetch. An actual current-selection change starts the newly selected occurrence, subject to start safety below. |

A row Low/High/Next adds **that row only**, not its surrounding collection. A collection adds its bounded complete ordered context. Priority comes from requested operation, not entity type. Existing upcoming Low/High/Next moves/retags the exact key (High boundary computed with that key virtually removed); current/played/missing keys fail stale. An unchanged position with changed origin/membership is a real edit, not no-op.

**Superseding user rule:** “does it change what the "currently playing" track is? then it should start playing, otherwise the pause/playing state stays at what it was”. For **queue intents**, perform the unchanged priority/placement and intentional selection rules first. Compare the exact receiver-authoritative current occurrence before/after that operation, not track IDs, displayed indices or play/pause flags. Same track ID in a different duplicate occurrence is a different selection. If current selection stays the same, preserve its play/pause state, current position and buffered intent: no media prepare/restart/resume/seek or promotion of a future head merely because paused, idle, ended or failed. A deduplicated/all-already-positioned edit with unchanged current cannot resume it. A real current-selection change starts the newly selected occurrence, subject to authority/focus/blocked/media/supersession safety; initially no current becoming selected may start. Attempt that selection once, without an automatic skip/retry search. No authority/selection/available output, transfer or quarantine means no queue mutation or deferred intent. Queue-only Low/High/Next never acquire output. **Latest explicit-app-Play correction:** deliberate app Play / Play now may reuse landed first-Play admission (`requireUnselected:true`, exact self target, route/session/lifetime fences) before executing an OWNED Now when the fresh room has no selected output. Stage blank paused activation for replacement Play, validate raw handoff metadata before keeping staged metadata coherent, and never briefly start retained old audio/history. An unavailable selected remote is still selected and cannot be stolen or retargeted. Prepared-only system/headset/notification Play cannot claim/import restored display. This exception is mobile admission, not an incompatible wire semantic. Do not invent a different queue order to manufacture a selection change.

**Mandatory corrected example:** A paused at 0:42, pending High H1, Low C1/C2; add Low album B `[B1,B2]` → queue `[A,H1,C1,C2,B1,B2]`, **A remains current and paused at 0:42**, H1 remains pending High and B stays Low. Terminal feedback **“Queued B”**, playback unchanged, null playbackKey; never “Started H1” or “Playing B”. The same unchanged-selection edit while playing/buffering preserves that state too. High X then acknowledged fresh-binding Y during active/buffering `A | M1 M2 C1 C2` still yields `A | M1 M2 X Y C1 C2`. Empty Low installing its initial current may start without turning its origin High. Explicit Now to another duplicate occurrence starts that exact new current even if its track ID equals A's.

This intentionally supersedes **both** 07's paused-context replacement and the earlier FEAT-023 inactive-head-start/count0-resume proposal. Nonstarting queue edits that leave current unchanged remain nonstarting; new initial selection or deliberate Now selection changes may start. Old paused-A→H1 vectors/tests are obsolete requirements, not regressions to preserve. **Dedicated explicit transport Play/Resume/Pause retains its normal semantics and is not constrained by this queue-edit rule. Passive composition/startup/restoration/browsing/service recreation/reconnection/lease renewal still never autoplay**; the selection-change start helper must remain scoped to the authorized queue transaction, not passive imports or transport gating. Explicit Pause/Stop while preparation is pending cancels that work, not a later delayed start.
