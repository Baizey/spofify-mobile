## Acceptance contract — one complete UI feature

1. **Listening-first header, both manual and derived.** Meaningful playlist title, optional **nonblank** description, at most **one** useful song-count/metadata line, primary Play (when capable), and **one accessible playlist More** integrated with this header/primary action area. No empty description slot, redundant standalone toolbar row, adjacent second More, always-visible kind/live-input/completed-evaluation inventory, edit/delete/copy bars or permanent bulk-limit paragraph. Do not invent zero counts while loading/unevaluated; a normal count describes the full known collection, not just visible rows.
2. **Consolidated secondary actions.** Refresh, Edit details, Edit rules, Make editable copy, Delete and Reorder remain reachable through that existing consolidated playlist overflow as capabilities permit. Existing collection Queue Low / Queue High / Play next / Play now stay intuitive/reachable there, using existing exact captured selection/binding/origin. Menu remains available for management/recovery even when queue-intent callbacks are absent. Preserve all busy/blocked/stale/capability checks, delete confirmation, retained drafts, revision conflicts and uncertain-copy verification/review acknowledgment; relocating controls never silently grants write authority or retries a write. Use native menu/sheet/dialog appropriate to the action count, not a new framework.
3. **Actual shared music rows in ordinary browsing.** Manual and derived rows use the existing `MusicRow` rendering/typography/artwork/line envelopes/action slots and `MusicListLayout` rhythm, not merely copied constants. No extra 10dp between songs, no stacked per-song remove button and no inline Play/Pause. Move exact manual-occurrence Remove into its existing row More, with existing confirmation and write safeguards. Keep all ID-backed artists/album, details, Like and Add-to-playlist actions intentional and reachable. Missing artwork/audio, one/many/long/Unicode credits and background refresh must retain the same pitch at each font scale as Home/Search.
4. **Keep exact action identity and accessibility.** Retain lazy keys by manual entry ID / derived occurrence ID, original signed selection tokens, revision/fence/context, exact current-occurrence highlight/Playing/Paused/Buffering and existing `captureCurrent`/row lifetime/source-generation guards. Do not highlight every duplicate or every context sharing a track ID. Tap opens details; More/long press/custom More and named Play now / Queue High retain proper enablement and 48dp targets. Physical-right High and its accessibility/More alternatives retain scoped gesture cancellation and fresh unselected-High origin captured at action start; never replace it with a fabricated interaction key or updated binding. List keys remain distinct from mini-player transport keys. More target and vertical scroll/edge Back are not swipe traps.
5. **Explicit reorder mode is the exception.** Existing complete bounded snapshot/revision checks, exact occurrence permutation, drag handles and accessible Move up/down, Save/Cancel may remain an intentional editing layout. Normal browsing must not inherit its stacked controls. Do not redesign the recipe editor, catalog, playlist index or app shell.
6. **Contextual truth, not inventory.** Preserve useful loading/error/empty/staleness recovery only when relevant, in concise plain language, retaining usable rows during refresh. Keep limits at **1,000**, exact late-selected-occurrence behavior and truthful action-specific partial-playback/copy-limit/refusal feedback. Copy confirmation may explain its own limit; uncertainty must still require verification rather than false success. No queue/backend/control/playback-policy change, passive preparation/autoplay/device claim or source/Go edits outside this UI scope.

FEAT-118 separately owns replacing paging/See-more mechanics with automatic continuous batches, including narrowly superseding old See-more UX documentation. FEAT-117 can land with existing paging behavior; do not turn shared-file overlap into a dependency or bundle them.
