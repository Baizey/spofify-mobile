# Mobile release operations

`Baizey/spofify-mobile` stays **private**. Official APKs go only to the separately provisioned public `Baizey/spofify-mobile-releases`. The release workflow builds an unsigned APK on private `main`, signs it in a protected job, and publishes it from a separate protected job. CI does not publish and requires no secrets. Debug remains `dev.spofify.mobile` with its existing Android debug signing and data. Release is `dev.spofify.mobile.release` with its own signer and data. Nothing migrates or copies between the two apps.

## One-time bootstrap (operator only)

1. Provision the public distribution repo with an independent `main` branch and a benign initial commit. **Do not fork or mirror the private source or copy its Git history.** Keep this repo dedicated to this stable channel, and prevent out-of-band release creation, asset edits, tag changes/deletion and concurrent edits to public `main` during deployment. Prefer tag/immutable-release protections where available, without blocking the designated App from creating official releases. Never delete a published `mobile-v…` tag; keep a release ledger or backups. If both a release and its tag are deleted, GitHub cannot tell the workflow that its version code was previously used.
2. On the private source repository, protect `main` with reviewed changes, including workflow, scripts, build and anchor changes. Create both environments `mobile-release-signing` and `mobile-release-deploy` **before adding secrets**. Restrict each to `main`, require independent reviewers and prevent self-review/admin bypass as available. Store credentials only in their matching environment, never as repository-wide secrets. If the repository plan cannot enforce independent protected deployments for a private repository, that is a rollout blocker; do not substitute unprotected secrets. The workflow alone cannot configure or verify these settings.
3. Privately generate and back up a dedicated, long-lived Android app-signing key in a PKCS#12 keystore. For example, in a private directory on a trusted workstation, use `keytool -genkeypair -storetype PKCS12 -keystore mobile-release.p12 -alias spofify-mobile-release -keyalg RSA -keysize 3072 -validity 10000` and enter an appropriate name and strong password interactively. Do not use the standard Android debug key, a disposable fixture key, or a server key. Maintain tested encrypted offline backups and accountable access. Use your keytool's PKCS#12 password conventions (typically the key password equals the store password).
4. Export **only the public certificate** and compute its SHA-256 over DER. Confirm it independently with the certificate exported from the standing keystore. Commit the 64 hex digits alone to [`scripts/mobile-release-cert.sha256`](../scripts/mobile-release-cert.sha256) in a reviewed change before dispatch. `UNCONFIGURED` deliberately blocks official releases. Do not update the anchor to make a failed signing job pass; losing the standing key or changing signers requires a separate Android update-compatibility plan.

   ```sh
   keytool -exportcert -storetype PKCS12 -keystore mobile-release.p12 \
     -alias spofify-mobile-release -file mobile-release-cert.der
   sha256sum mobile-release-cert.der
   ```

5. In `mobile-release-signing` only, provision secrets `MOBILE_KEYSTORE_B64` (single-line base64 of the PKCS#12 file), `MOBILE_KEYSTORE_PASSWORD`, `MOBILE_KEY_ALIAS` and `MOBILE_KEY_PASSWORD`. Do not print or commit base64, keystore, passwords or App private keys. Transfer them through the operator's approved secret-management channel.
6. Create a dedicated GitHub App with repository **Contents: read and write** (and GitHub's mandatory Metadata read), no other permissions or subscriptions, and install it **only** on `Baizey/spofify-mobile-releases`. In `mobile-release-deploy` only, provision variable `MOBILE_DISTRIBUTION_APP_ID` and secret `MOBILE_DISTRIBUTION_APP_PRIVATE_KEY`. The pinned action requests a short-lived installation token restricted to the distribution repo and Contents write, and revokes it at job end. The source workflow's `GITHUB_TOKEN` is read-only for checkout and is not used for distribution. If organizational policy precludes a GitHub App, a separately reviewed workflow change may use an expiring fine-grained token scoped only to distribution Contents write; never use a classic PAT or a token with access to private source.

## Publish a stable release

1. Verify ordinary CI green and complete the device acceptance gate below before authorizing rollout. Manually run **Publish Mobile Release** on private `main`. Supply a strictly increasing decimal `version_code` (`1`–`2100000000`, no leading zeroes) and display `version_name` (1–80 ASCII letters/digits or `.+_-`, beginning with a letter or digit). Gradle applies them to release only. The official tag derives exclusively from `version_code`; the display name is not an ordering key.
2. Review and approve signing and deployment separately. The deploy job confirms the public repo and its `main` anonymously, then pins the release tag target to that **public** `main` commit SHA, never a private SHA or source ref. It checks all paginated public distribution tags and releases (drafts and prereleases reserve their version codes too), and the anonymous latest channel. Duplicate, reused or lower codes are rejected; malformed reserved `mobile-v…` entries block publication. The gate runs again immediately before promotion. Private workflow concurrency serializes dispatches; exclusive write access to the public channel is required because GitHub does not offer atomic check-history-and-publish.
3. The workflow creates an empty stable draft, uploads the one verified APK, and waits briefly for GitHub's own digest. It checks that GitHub's digest and size match the signed bytes before promotion. No generated notes, private commit IDs, run IDs or custom metadata are sent to the public release. GitHub's automatic Source code archive links refer to the **public distribution repo** and are not uploaded assets.
4. Confirm job success and anonymous `GET https://api.github.com/repos/Baizey/spofify-mobile-releases/releases/latest`: `draft=false`, `prerelease=false`, tag `mobile-v<versionCode>`, and exactly one uploaded asset `spofify-mobile-release.apk` with positive exact `size` ≤ 150 MiB, `digest` `sha256:<64 hex>`, and URL `https://github.com/Baizey/spofify-mobile-releases/releases/download/<tag>/spofify-mobile-release.apk`. The workflow polls this endpoint and verifies the public tag target before declaring success.

If the draft digest never appears, the workflow fails and leaves the release a draft. Do not publish it manually or fill the digest yourself. If publication was attempted but final anonymous verification failed, the release may already be public. Investigate the release, asset and tag before making any changes. Do not retry a failed publication blindly, overwrite assets, remove a published tag, reuse a code, or change `latest` to roll back. After addressing the cause, only ship a correction with a higher code. Untouched failed drafts intentionally reserve their code.

## Offline checks and device acceptance

With JDK 25, Android SDK platform `platforms;android-37.0` and build-tools 36.0.0 provisioned, CI and operators can verify the build without release credentials:

```sh
python3 -B -m unittest discover -s scripts -p 'test_*.py' -v
./gradlew --no-daemon -PmobileReleaseVersionCode=12345 -PmobileReleaseVersionName=0.0.0-ci \
  :core:test :app:testDebugUnitTest :app:testReleaseUnitTest :app:assembleDebug :app:assembleRelease
bash scripts/test-mobile-signing.sh
```

The signing test uses fresh disposable keys and asserts debug identity, release identity/version, APK verification and wrong-signer rejection. Publication fixtures use mocked responses and perform no GitHub operations. None of these checks proves the real Windows/Linux runner image, GitHub App setup or a real GitHub publication; use the pinned Ubuntu workflow execution and operator review to validate hosted prerequisites. No emulator was available for pipeline verification; no installation was performed.

Before authorizing the first official release, on an isolated Android emulator/device profile, use two release builds signed with the **same disposable certificate** and increasing version codes, synthetic release metadata and synthetic local app data only. Confirm side-by-side debug and release, no copied data, and that the new release installs **over** the previous release without clearing app data. Verify version advances, the release's synthetic preferences/offline data remain, and the unrelated debug installation/data remain untouched. Confirm mismatched signer and downgrade are rejected. Check that switching to Work offline fences update work; if the persistence write fails it stays fenced until a successful offline→online transition or a subsequent app process successfully reads online state. For the installer handoff, verify the installer does not launch automatically, Android alone owns source approval and explicit install confirmation, and cancelling either prompt leaves the app/data unchanged. Do not use an existing user installation, standing key or live account for this acceptance gate.
