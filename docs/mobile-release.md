# Mobile release operations

Like Desktop, Mobile packages from canonical `main` and publishes to its own public [GitHub Releases](https://github.com/Baizey/spofify-mobile/releases). The manual workflow resolves the version pair in a small planning job, packages an unsigned APK in a read-only build job without release credentials or persisted checkout credentials, then signs and publishes it in one protected `mobile-release` job. The planning job runs on canonical `main` outside the protected environment. It grants the built-in `GITHUB_TOKEN` `contents: write` solely to see drafts ([GitHub requires push access to list draft releases](https://docs.github.com/en/rest/releases/releases#list-releases)); it performs no writes or release signing. Only the protected job has access to the release signing secrets and uses `contents: write` to publish. Ordinary CI does not publish and needs no secrets.

Debug remains `dev.spofify.mobile` with its existing Android debug signing and data. Release is `dev.spofify.mobile.release` with its own signer and data. Nothing migrates or copies between the two apps.

## One-time bootstrap (operator only)

1. On the public `Baizey/spofify-mobile` repository, protect `main` with reviewed changes, including the workflow, scripts, build and certificate anchor. Configure `mobile-release` **before adding secrets**: restrict it to `main`, require an independent reviewer and prevent self-review/admin bypass where available. The workflow cannot enforce environment settings by itself. Do not use unprotected secrets.
2. Publish mobile updates only through this workflow. Protect `mobile-v…` tags and published releases against edits and deletion where available, without blocking the workflow token from creating releases. Do not edit the canonical release title, and never delete a release and its tag: GitHub would no longer report that the version code was used.
3. Privately generate and back up a dedicated, long-lived Android app-signing key in a PKCS#12 keystore. For example, in a private directory on a trusted workstation, use `keytool -genkeypair -storetype PKCS12 -keystore mobile-release.p12 -alias spofify-mobile-release -keyalg RSA -keysize 3072 -validity 10000` and enter an appropriate name and strong password interactively. Do not use the standard Android debug key, a disposable fixture key, or a server key. Maintain tested encrypted offline backups and accountable access. Use your keytool's PKCS#12 password conventions (typically the key password equals the store password).
4. Export **only the public certificate** and compute its SHA-256 over DER. Confirm it independently with the certificate exported from the standing keystore. Commit the 64 hex digits alone to [`scripts/mobile-release-cert.sha256`](../scripts/mobile-release-cert.sha256) in a reviewed change before dispatch. `UNCONFIGURED` deliberately blocks official releases. Do not update the anchor to make a failed signing job pass; losing the standing key or changing signers requires a separate Android update-compatibility plan.

   ```sh
   keytool -exportcert -storetype PKCS12 -keystore mobile-release.p12 \
     -alias spofify-mobile-release -file mobile-release-cert.der
   sha256sum mobile-release-cert.der
   ```

5. In `mobile-release` only, provision secrets `MOBILE_KEYSTORE_B64` (single-line base64 of the PKCS#12 file), `MOBILE_KEYSTORE_PASSWORD`, `MOBILE_KEY_ALIAS` and `MOBILE_KEY_PASSWORD`. Do not print or commit the base64, keystore or passwords. Transfer them through the operator's approved secret-management channel. No separate GitHub credential is needed.

## How in-app updating works

The release app checks the anonymous latest release on foreground entry or return from Work offline, not on a background timer. A non-APK release such as `ci-broker-b6eb54f` is not an update. Completed checks are normally held for 30 minutes. A verified update stays ready without polling across foreground returns until the process restarts, Work offline fences it, or it fails revalidation. Installation requires a new explicit tap from Settings while the app is resumed and not playing locally, then Android's own confirmation. Debug has no update surface or installer permission.

Release records Work offline in its own versioned private policy file; it does not load or migrate the debug preference. Malformed or interrupted state starts offline, preserving local access; an explicit return online rewrites the policy. An unreadable policy fails closed. Test failure and recovery with synthetic app data only.

## Publish a stable release

1. Complete the device acceptance gate before authorizing rollout. Manually run **Publish Mobile Release** on `Baizey/spofify-mobile` `main` and choose `major`, `minor`, or `patch` (the default), as on Desktop. This is the only release input; you cannot supply `versionCode` or `versionName`.
2. Before packaging, the planning job resolves both values from all pages of canonical GitHub release and tag history using authenticated API requests. It checks anonymous latest for consistency but does not use it to select the version pair.
   - **`versionName`**: Apply the chosen bump to the numerically highest strict `X.Y.Z` from a published stable Mobile release with exactly the title `Spofify Mobile X.Y.Z`. Each component is a canonical decimal integer from `0` to `4294967295` (`2^32−1`), with no leading zeroes. With no published stable Mobile release, start from `0.0.0`. A published stable `mobile-v…` release with a missing or malformed title blocks publication; the workflow does not guess a replacement version. A `major` bump resets minor and patch to zero, and a `minor` bump resets patch to zero. Drafts and prereleases do not set this baseline.
   - **`versionCode`**: Use one more than the highest code in any `mobile-v<code>` tag or release, including drafts, prereleases and tags with no release. The first code is `1`; codes are canonical decimal integers in `1`–`2100000000`. Unrelated entries such as `ci-broker-b6eb54f` do not affect either value. Malformed `mobile-v…` entries or an out-of-range next value block the release.

   Gradle applies the resolved pair to the release variant only. The package job repeats Mobile CI checks on the exact dispatch SHA, including both variants and disposable signing.
3. At the `mobile-release` approval, review the dispatch SHA, selected bump, resolved pair and successful package job, with the unsigned artifact still available (one-day retention). Cancel stale approvals; subsequent changes to `main` do not change the packaged revision. Reruns are blocked; inspect for partial publication before starting a new dispatch.
4. Before signing and again before and during publication, the protected job re-resolves the expected pair from the same authenticated canonical history and checks anonymous latest for consistency. If either value drifts, it stops rather than changing the packaged versions. It verifies the APK's exact release identity and resolved code and name, and verifies the signed APK against the pinned certificate. The job uploads exactly one APK to a draft, checks GitHub's own digest and size, and rechecks history. It creates a new lightweight `mobile-v<versionCode>` tag at the exact packaged SHA and promotes the draft to stable latest with the exact title `Spofify Mobile <versionName>`. During rechecks, the run verifies its own draft and tag once created rather than treating them as external reservations. No other run may reuse that draft or tag. GitHub's automatic source archives are not uploaded assets. Workflow concurrency serializes its own dispatches. Use this workflow as the only writer of `mobile-v…` tags and releases: GitHub cannot atomically compare history and promote a draft. The post-promotion check reports a competing stable release but cannot undo a conflicting out-of-band write.
5. Confirm job success and anonymous `GET https://api.github.com/repos/Baizey/spofify-mobile/releases/latest`: `draft=false`, `prerelease=false`, tag `mobile-v<versionCode>`, exact title `Spofify Mobile <versionName>`, and exactly one uploaded asset `spofify-mobile-release.apk` with positive exact `size` ≤ 150 MiB, `digest` `sha256:<64 hex>`, and URL `https://github.com/Baizey/spofify-mobile/releases/download/<tag>/spofify-mobile-release.apk`. The workflow polls this endpoint with a 128 KiB response cap, verifies the tag SHA, then anonymously streams the canonical download and checks byte count and SHA-256 against the signed APK. It follows only bounded HTTPS redirects to the exact `release-assets.githubusercontent.com` host.

If the draft digest never appears, the workflow fails and leaves the release a draft. Do not publish it manually or fill the digest yourself. If publication was attempted but final anonymous verification failed, the release may already be public. Investigate the release, asset and tag before making any changes. Do not retry a failed publication blindly, overwrite assets, remove a published tag, reuse a code, or change `latest` to roll back. After addressing the cause, only ship a correction with a higher code. Leave failed drafts untouched: they intentionally reserve their code but do not advance the stable `versionName` baseline.

## Offline checks and device acceptance

With Java 25, Android SDK platform `platforms;android-37.0` and build-tools 36.0.0 provisioned, CI and operators can verify the build without release credentials. The hosted build jobs use Temurin 25 to start Gradle and SDK tools; the Gradle daemon is pinned separately to JetBrains Runtime 25 by `gradle/gradle-daemon-jvm.properties`. A fresh build runner without matching JBR 25 must be able to reach Foojay and its JBR download destination. For offline builds, provision JBR 25 and the wrapper/dependencies before starting; having Temurin alone is not enough.

```sh
python3 -B -m unittest discover -s scripts -p 'test_*.py' -v
(
  export ANDROID_USER_HOME=$(mktemp -d)
  trap 'rm -rf -- "$ANDROID_USER_HOME"' EXIT
  ./gradlew --no-daemon -PmobileReleaseVersionCode=12345 -PmobileReleaseVersionName=0.0.0-ci \
    :core:test :app:testDebugUnitTest :app:testReleaseUnitTest :app:assembleDebug :app:assembleRelease
  bash scripts/test-mobile-signing.sh
)
```

The signing test uses fresh disposable keys and asserts debug identity, release identity/version, APK verification and wrong-signer rejection. Publication fixtures use mocked responses and perform no GitHub operations. None of these checks proves the hosted runner, protected environment settings, real GitHub CDN routing or a real publication; use hosted CI and operator review to validate prerequisites. No emulator was available for pipeline verification; no installation was performed.

Before authorizing the first official release, on an isolated Android emulator/device profile, use two release builds signed with the **same disposable certificate** and increasing version codes, synthetic release metadata and synthetic local app data only. Confirm side-by-side debug and release, no copied data, and that the new release installs **over** the previous release without clearing app data. Verify version advances, the release's synthetic preferences/offline data remain, and the unrelated debug installation/data remain untouched. Confirm mismatched signer and downgrade are rejected. Check that switching to Work offline fences update work; if the persistence write fails it stays fenced until a successful offline→online transition or a subsequent app process successfully reads online state. For the installer handoff, verify the installer does not launch automatically, Android alone owns source approval and explicit install confirmation, and cancelling either prompt leaves the app/data unchanged. Do not use an existing user installation, standing key or live account for this acceptance gate.
