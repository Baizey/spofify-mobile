# Native playback devices

## Status and validation boundary

The production endpoint capability is **enabled in source**: the application-owned coordinator uses the Media3 service endpoint and authenticated player API, with service-lifecycle registration rather than a test-only capability override. The device sheet is view-only without a registration and exposes selected-output controls when registered. This is not a claim of native handoff/audio/background acceptance.

**Native handoff runtime / rendered-app validation is not complete.** Earlier isolated AVD attempts failed before app launch; their results do not establish current environment health. Normal isolated synthetic AVD validation is allowed under [ui-validation.md](ui-validation.md). Robolectric and compiled instrumentation are development evidence, not actual Android audio, screen-lock, power-management or vendor-background approval. Record the API/runtime actually exercised; do not infer older-version or hardware coverage from source review or cached test runtimes.

## One output, same-account coordination

The application owns one coordinator per authenticated client, and `PlaybackService` owns the only Media3/ExoPlayer output. Activity recreation, picker dismissal, player collapse and controller release do not create a second player or reregister a still-valid service connection.

The existing authenticated `GET/POST /api/me/player` protocol coordinates available same-account players. Selecting an output uses acknowledged **prepare → release → activate**, not an arbitrary URL or a freshly fetched saved playlist. A remote display is only display/control state; it is never local audible progress or local history. Native outgoing transport uses explicit Pause/Resume. Legacy incoming Toggle is resolved by the actual authoritative output, not a possibly stale remote display.

Preparation validates the complete snapshot without replacing a queue, opening audio, starting playback or writing history. Activation requires current coordinator authority and session/generation checks. Actual readiness/start results determine `ok`, `blocked`, `media` or `rejected`; receiving a directive alone is not a successful playback ACK.

## Explicit first app Play in an unselected room

A deliberate app musical Play retains its exact prepared selection and originating route/session/request fence while binding. If the current device already has legitimate idle ownership from pristine registration, normal explicit execution applies. Otherwise a serialized device-scoped fresh observation must show no selected output or pending recovery/work before the client sends one typed `claimUnselected` request: ordinary `transfer` plus exact-self target, current epoch, monotonic selection sequence and literal `requireUnselected: true`. Unsupported/older servers fail closed; there is no ordinary-transfer fallback. Rounded public lease/quarantine values never replace server admission.

The memory-only, latest-payload admission is bounded to twelve seconds and cannot reroute to a competing owner. Its matching prepare/activate must stage empty paused state for replacement Play (or the exact captured live paused queue for deliberate app Resume), then receive matching terminal activation-ACK acceptance before requested playback executes once. Preparation/active-ID display is not a start permit. Uncertain writes/ACKs, expiry, Pause/Stop, output choice, stale origin/session/service and authority loss retire the musical intent; subsequent polling/reconnect never replays it. System/headset/notification prepared-only Play, Add, Play next and queue edits do not enter this conditional-acquisition path. Their established behavior under already-legitimate authority is unchanged.

Native first-Play rendering/audio/history/background acceptance remains **blocked / not complete** under the current isolated-emulator assessment; protocol/service JVM tests and compiled fixtures are not installed-app approval.

## Prepared Pause/Resume admission

Local output can already be paused while its exact paused-state publication still awaits confirmation. A second ordinary Resume is correctly refused during that window, not queued for later replay. The mini-player, expanded player and posted playback notification expose the refusal and its recovery guidance; a fresh deliberate Resume after settlement starts the retained occurrence. Refusal presentation is tied to its original action and cannot label a changed queue/output or hide a later admitted start. Queue-only edits remain distinct from transport: unchanged-current Low/High/Next does not resume it.

The production-path regressions use actual AppGraph/ViewModel/Connection/service/coordinator/API controls, a real Media3 state machine with synthetic PCM, and separately provisioned persistent pinned Go integration tests. Settled Pause→Resume success is checked by observed isPlaying plus progress, not by an optimistic icon or HTTP acceptance. See [prepared transport testing](prepared-transport-testing.md) for the portable unit baseline and mandatory opt-in integration gate. These observations are not installed-Android/acoustic or rendered-app approval.

## What persists — and what does not

Android Keystore-encrypted local metadata stores an installation UUID and accepted device name, bound to the exact server origin and immutable account ID and excluded from app backup/transfer. This makes the local installation/name more persistent than a screen or login session. It stores no credentials, playback intent, queue or server-issued device authority.

The server accepts **`register {name}`** and returns a **fresh, login-session-bound, ephemeral device ID**. A local installation UUID is not that protocol ID. Expired, revoked, logged-out or reconnected sessions cannot reuse a previous registration as authority. The application coordinator survives UI reattachment and polls while its service lifecycle is valid. An uncertain dispatched registration has a process-local 30-second minimum spacing, shared across graph reconfiguration; repeated Retry cannot reset it. This stores no credentials, device IDs or authority, and a genuinely new process has no retained ambiguity record. The spacing reduces churn, **not** proof that an unknown registration expired: the server can accept a delayed request after caller cancellation.

Graceful service/graph disposal immediately fences output and ordinary client auth/work, then gives the known exact ID one separate cleanup-only opportunity. Its four-second capture-relative bound includes transport-lock waiting; it cannot register, publish, select, follow redirects, retry or borrow a successor session. Cleanup reuses only a captured, previously connected direct exact-origin address, preserving the origin hostname and TLS verification without fresh blocking DNS/proxy discovery. With no eligible route (including a proxied-only connection), it fails closed and leaves broker expiry/drain as the fallback rather than retaining a credential-bearing resolver indefinitely. A successor registration waits for that bounded attempt. Successful leave removes only the exact old row; genuine same-name endpoints survive. Losing a leave response never replays it. A remote rename target's 404 is not evidence that this phone's registration disappeared; self-scoped polling separately establishes actual registration loss.

**Abrupt-death / unknown-acceptance duplicates remain OPEN.** The current broker offers no installation-bound registration idempotency/recovery/replacement. A lost accepted register response, late acceptance after cancellation, or death before leave can retain both an orphan and a successor with the same cookie/name. Availability lasts at most 5 seconds, leases/drain up to 8 seconds and registrations are request-pruned at 30 seconds since their last accepted heartbeat—not since the client's timeout. No name filtering/deletion, receiver rotation or stored stale authority hides these windows. Immediate crash-proof single-row identity requires an authenticated backend recovery/replacement contract that also fences or drains prior authority.

Restoration, process/service recreation, lease loss and uncertain reconnection stay **paused**. There is no startup autoplay, deferred old Play, offline autoplay or durable queue-resume promise. A new explicit Play or transfer may activate only after current server acceptance and fresh authority. A dead/restricted app is not advertised as magically reachable.

## Queue, progress and history safety

Exact snapshot import/export retains duplicate occurrences, queue keys, realized traversal, unshuffled baseline order, context and per-occurrence context, current position, repeat/shuffle, notices and truncation, and current history nonce/progress/reported state. Complete state must be publication-safe: the existing player protocol permits a 2MiB outbound body; admission reserves 16KiB for worst escaped envelope/history/context/scalar growth. Per-field-valid oversized input is decoded but rejected before queue/history/media mutation, never truncated. Final rekeyed replacements and combined enqueue/undo candidates are preflighted; two individually safe batches cannot silently create an unpublishable queue. Media3 uses millisecond seeks; unchanged paused wire elapsed and imported progress retain their fractional precision rather than inventing local audible credit.

Audio URLs are rebuilt only from track IDs through the current exact-origin authenticated client. Incoming metadata cannot supply a network URL, cookie, private path or mutable playlist refresh during handoff. New explicit musical selections may use the existing authenticated playback endpoints; restoration/import/Resume do not refetch collections. Positive Play of the already-current occurrence preserves its prepared queue, position and history traversal.

Pause, output revocation, logout, focus loss and becoming-noisy events invalidate stale starts and stop/discard buffered output. Upstream ViewModel and manual/derived playlist fetches capture the cancellation generation before awaiting their queue; an old response cannot return as a new Play or enqueue intent. Posted transport/queue callbacks and notification tokens are fenced, including queue changes and service identity. Imported position is not locally listened progress. History qualification still requires genuinely new observed audible progress, preserves the transferred event nonce and never retries an uncertain history write.

Internal Close silences and empties output, releases focus and removes foreground/notification synchronously. The matching final execution ACK and exact empty snapshot get **one bounded publication attempt** before service disposal. Publication failure, cancellation or timeout never replay Close. A service-instance-scoped fail-safe retains cleanup if result delivery is lost. A newer queued intent holds rather than abandons that cleanup; a stale/rejected replacement returns it, and only installed nonempty replacement state protects the new queue. A retained bounded watchdog cancels stalled uninstalled work before disposal. Held old completions/timers cannot stop a successor service or installed queue.

## Transient interaction interface

`PlaybackState.interactionKey: PlaybackInteractionKey?` is an opaque, in-process identity for held gestures. It is not server authority and must not be logged, persisted, saved in saved-state or placed in media extras. Null means unavailable. It binds the actual client/session incarnation, service/coordinator/output authority incarnation, authoritative queue and current occurrence. Equal same-account login values do not reuse the old session identity. Queue replacement, current transition, authority loss, reconnection or service replacement invalidates it. Progress, buffering, duration and same-owner heartbeat/lease renewal do not; deadlines, state sequence/age and whole coordinator state are deliberately excluded. The coordinator records semantic queue/current/authority binding changes on every accepted publication, so an unsampled A→B→A transition still invalidates a held remote interaction.

`PlaybackState.canMoveUpcomingAbsolutely` defaults to false for unknown controls and remains false for remote outputs. Local enabled authority supplies a key and absolute-drag capability. UI captures the key at gesture start and cancels when it changes; catalog swipe can use the same cancellation identity. The guarded move interface does not itself provide prepared enqueue with an expected key; do not assume all queue operations share that protection.

`PlaybackControls.moveUpcoming(expectedKey: PlaybackInteractionKey, occurrenceId: String, toIndex: Int)` uses zero-based displayed-upcoming indices. Locally it rechecks the key, exact occurrence and target at the actual serialized service mutation, after coordinator waiting. It does not initialize/import output to make a stale gesture valid. A changed drop commits one queue edit and exits shuffle while preserving current audio item/position/history/context; preview/cancel, invalid targets, stale keys and same-index drops do not edit or prepare/start/seek. Remotely the same overload permits only one representable directional command (`up`, `down`, or `next`); arbitrary drag remains disabled and no step chain or legacy fallback is used. The original wire occurrence key and expected client/session/output/queue identity are revalidated at coordinator dispatch. Existing unguarded two-argument controls remain source-compatible for accessible legacy actions.

Regressions exercise actual connection/service queued-dispatch races, duplicate tracks, same-account reauthentication, service recreation, authority replacement with unchanged IDs, remote transport waits with queue/owner/session replacement, unavailable endpoints, and a held key across twelve local and twelve remote benign lease/progress heartbeats. They retain existing protocol/startup/history/focus/close tests. This is source/automated evidence only; native gestures, audio and background acceptance remain unverified.

## Negotiated priority queue intents

The mobile successor consumes landed Go FEAT-023 `b6eb54ffdc91e07e2ce7824b8be5f90afa8b05eb` and its byte-exact frozen corpus under `core/src/test/resources/queue-intents-v1/`. Recursive legacy DTO shapes remain strict; capability belongs to a fresh authenticated registration, not output name, availability or remote/local presentation. Native receiver advertisement is tied to the complete metadata/revision/import/normalization/detail-ACK implementation.

Physical-right row swipe and default manual queue mean **High**. Existing intentional More flows expose **Queue Low / Queue High / Play next / Play now**; row Low/High/Next selects only that row, while collection actions prepare the bounded complete context at the leased receiver. Low appends; High is FIFO after the last pending High occurrence without repartitioning explicit interleaving; Next is immediately upcoming and marks pending High; Now deliberately replaces the requested context or jumps the exact upcoming key. Duplicate manual entry and signed derived path/token selection remain exact. No inline Play slot or row/dock geometry redesign is introduced.

The receiver performs placement/selection first, then starts once **only if the exact current occurrence changes**. Same track ID at a different duplicate key is a change. Paused A at 0:42, pending H1 and Low C1/C2 plus Low album B leaves `[A,H1,C1,C2,B1,B2]`, A current/paused at 0:42, H1 pending and B Low; receipt is queued/count2/low/unchanged/null playbackKey. Unchanged current preserves actual playing/buffering/idle/error state as well: no prepare/restart/seek/resume, inactive-head promotion or count0 resume. Requested origin for every retained occurrence is separate from upcoming pending High membership. Capable handoff preserves origins/High/history with no refetch. Missing legacy metadata preserves the full musical snapshot, sets origins legacy, clears pending High and records legacy-reset; unknown versions are rejected, not treated as missing. Receiver incarnation is service-owned and independent of import. Semantic revision fences unsampled queue/current/history-event/provenance/shuffle/repeat ABA, excluding progress, duration, lease renewal and play-state flags alone.

Terminal detail separates acceptance from playback. Positive accepted blocked/media queue changes are retained, not rolled back or resent. ## Android media buttons and music-stream volume

The existing service/session owns all transport; there is no second player or Activity key dispatcher. Admitted Play, Pause, Stop-as-Pause, Play/Pause, single Headset Hook, Next/Previous and Skip variants route through the coordinator. Fast-forward/rewind use bounded relative seeks against the selected output's prepared position/duration. Positive Play operates the existing in-memory prepared occurrence, not a new catalog selection or a restored/server queue. A remote selection exposes its authoritative snapshot as a read-only metadata/timeline/state projection, independent of an empty or stale local ExoPlayer queue; available skip/seek commands reflect that selected queue. Unsupported index-addressed remote requests are not interpreted using the local timeline. Raw local metadata/state callbacks are suppressed while remote is displayed; the existing main service tick publishes remote changes. This creates no audio URI/configuration, local history credit, remote volume or start authority.

The custom headset policy is **one immediate action per distinct non-repeated key-down**. Key-up, held-key repeats, duplicate delivery and events predating service creation, suspension, prepared queue/current changes or accepted output-binding changes are consumed without another command. Impossible/future key timestamps fail closed. Relative seeks share the projection's normalized elapsed/duration, including known track-duration fallback. Notification PendingIntent identity and delivery admission bind the selected-output/queue incarnation; a retained token cannot be upgraded to operate a replacement remote queue, while benign progress heartbeats do not retire it. Headset Hook/Play-Pause are not delegated to Media3's delayed single/double-tap timer, which would otherwise re-admit old Play after cancellation. This is not a universal headset multi-click mapping promise. Genuinely unmapped keys from admitted callers are left available to platform handling; rejected callers never borrow Media3's notification-controller fallback identity.

Media3 1.11.1 leaves the legacy media-button caller's `isTrusted` flag unset. The button-specific compatibility check uses platform media-control trust on API28+ without requiring app-side package visibility; ordinary connection admission and queue/URI/raw mutator restrictions remain unchanged. Unknown UID and missing framework attribution fail closed. **API26–27 legacy media-button delivery normally lacks a UID in Media3 and therefore remains a compatibility limitation requiring further authenticated-attribution evidence; newer-API source/JVM tests do not establish that older path.**

## Android background limits

Foreground promotion and audio focus are distinct prerequisites, not substitutes for coordinator authority. Android remains responsible for enforcing foreground-service/background-start and notification restrictions. Unsolicited background handoff to an idle/restricted phone reports **Needs a tap / blocked** rather than claiming playback. A currently running foreground output can continue; a freshly fenced notification/system-media user action may ask Android to evaluate its permitted user-interaction exemption, and still fails safely if Android refuses.

ExoPlayer's internal focus-gain auto-resume is disabled. Focus is requested only for an authorized explicit start; denied/delayed focus does not schedule later autoplay. Loss/transient loss/ducking and noisy events stop local output. A subsequent gain never resumes it. Terminal playback/error relinquishes focus and foreground ownership; bound UI may retain paused state, but an unbound stopped service is disposable.

This is not Chromecast, synchronized multi-room audio, a relay, a wake service for a killed app, an exemption from Doze/battery limits, or a guarantee that registrations survive login changes. Notification/headset/Bluetooth, real background/lock-screen delivery, audio decoder/device behavior and OEM power limits remain unverified until an approved isolated native journey (and only genuinely hardware-specific checks separately coordinated through the user) can run.
